# Artifacts and formats

Every claim in this project is backed by a file. This page describes each
format so you can read, diff or regenerate them without guessing.

---

## `reports/` — evidence documents

All five are committed, machine-readable, and regenerated by a command (see
[CLI](cli.md)). Each carries a `timestamp` and a `hardware` string, so a stale
or foreign-machine file is identifiable at a glance.

### `eval_report.json` — accuracy

Written by `python -m src.models.evaluate`.

```json
{
  "model": "best.pt",
  "data": "configs/dataset.yaml",
  "split": "val",
  "imgsz": 320,
  "images": 270,
  "hardware": "Windows-10-10.0.26300-SP0 | Intel64 Family 6 … | python 3.11.7",
  "timestamp": "2026-10-25T10:44:34+00:00",
  "mAP50": 0.7208593384148835,
  "mAP50_95": 0.4191165798397718,
  "precision": 0.6577969755601648,
  "recall": 0.6982250905072714,
  "training": {"model": "yolov8n.pt", "epochs": 50, "batch": 16,
               "imgsz": 320, "device": "cpu", "optimizer": "auto"},
  "per_class": {"crazing": {"mAP50_95": 0.15460208198193207}, "…": {}}
}
```

* `split` + `images` state exactly which data was scored.
* `training` is read from the run's `args.yaml`, i.e. what was executed, not
  what was requested.
* `per_class` keys are the model's class names in head order.

### `benchmark.json` — latency with the shipped session options

Written by `python -m src.models.benchmark`.

```json
{
  "model": "industrial_yolov8n.onnx",
  "model_input": [1, 3, 320, 320],
  "provider": "CPUExecutionProvider",
  "hardware": "…",
  "warmup_runs": 50,
  "benchmark_runs": 200,
  "allow_spinning": false,
  "timestamp": "…",
  "mean_inference_ms": 32.77712050017726,
  "median_inference_ms": 36.0823499977414,
  "p95_inference_ms": 45.79945500154281,
  "p99_inference_ms": 59.16023899895661,
  "mean_e2e_ms": 40.97464500038768,
  "throughput_fps": 24.40533651946316
}
```

`*_inference_ms` is pure `session.run`; `mean_e2e_ms` includes letterbox
preprocessing and NMS. `throughput_fps` is `1000 / mean_e2e_ms`.

### `benchmark_spinning.json` — the same protocol with ORT's default pool

Identical schema, `"allow_spinning": true`. Exists so the latency correction
can be re-checked rather than taken on trust: median 244.99 ms vs 36.08 ms.

### `loadtest.json` — service-level throughput

Written by `scripts/loadtest.py`, one entry per concurrency level.

```json
{
  "url": "http://127.0.0.1:8123/v1/detect",
  "deployment": "single uvicorn worker, 1 CPU, ONNX Runtime CPUExecutionProvider",
  "note": "API rate limit raised to 100000/minute for the run …",
  "hardware": "…",
  "timestamp": "…",
  "image_kb": 21.1,
  "scaling": [
    {"concurrency": 8, "requests": 240, "throughput_rps": 25.8,
     "wall_seconds": 9.3, "ok": 240, "failures": {},
     "latency_ms": {"mean": 305.8, "p50": 297.8, "p95": 460.6,
                    "p99": 555.7, "max": 568.3}}
  ]
}
```

`failures` maps non-200 status codes to counts; an empty object is the only
acceptable value for a quoted run. `note` records the rate-limit override,
because a 60 req/min limit would otherwise dominate the measurement.

### `quantization_tradeoff.json` — FP32 vs INT8

Written by `python -m src.models.quantize --compare <frames_dir>`.

```json
{
  "hardware": "…", "timestamp": "…", "frames": 24,
  "warmup_runs": 10, "benchmark_runs": 50,
  "models": {
    "fp32": {"file": "industrial_yolov8n.onnx", "size_mb": 12.65,
             "mean_ms": 21.58, "median_ms": 19.46, "p95_ms": 36.91},
    "int8": {"file": "industrial_yolov8n.int8.onnx", "size_mb": 3.36,
             "mean_ms": 309.84, "median_ms": 291.6, "p95_ms": 417.01}
  },
  "detection_agreement": {"frames_compared": 24, "identical_classes": 12},
  "int8_speedup_median": 0.07
}
```

`int8_speedup_median` is `fp32_median / int8_median`: **below 1 means INT8 is
slower**. `detection_agreement` compares the sorted class-id set per frame, so
it measures "did the model find the same defect types", not box geometry.

## `data/processed/` — dataset layout

```
data/processed/
├── images/
│   ├── train/*.jpg      1260 (NEU-DET) or 240 (synthetic)
│   ├── val/*.jpg         270 or 50
│   └── test/*.jpg        270 or 50
└── labels/
    ├── train/*.txt
    ├── val/*.txt
    └── test/*.txt
```

One dataset exists at a time; building either replaces the other. Labels use
standard YOLO format, one box per line:

```
<class_id> <x_center> <y_center> <width> <height>
0 0.512300 0.481000 0.204000 0.150000
```

All four geometry values are normalized to `[0, 1]`. An **empty** `.txt` (or a
missing file) is a legitimate clean frame, not an error — `DatasetValidator`
counts it as `clean_images` rather than flagging it.

### Dataset YAML

```yaml
path: data/processed
train: images/train
val: images/val
test: images/test
names:
  0: crazing
  …
```

`configs/dataset.yaml` describes the real dataset,
`configs/dataset_synthetic.yaml` the CI one. They point at the same root, which
is why the two datasets are mutually exclusive.

## `models/` — model files

| File | Size (this machine) | Role |
|---|---|---|
| `industrial_yolov8n.onnx` | 12.65 MB | The served graph (`MODEL_PATH`) |
| `industrial_yolov8n.pt` | ~6.5 MB | Ultralytics checkpoint; used for evaluation/export and the PyTorch fallback |
| `industrial_yolov8n.int8.onnx` | 3.36 MB | Dynamically quantized graph, kept as evidence; **not** served |

The ONNX input shape is `[1, 3, 320, 320]`. A graph exported at a different
size still loads, but the letterbox step rescales to the baked-in shape — keep
`--imgsz` consistent between training, export and expectation.

## `runs/` — training output

`runs/detect/industrial_defect_yolov8n/` is Ultralytics' own directory:
`weights/best.pt`, `weights/last.pt`, `results.csv` (per-epoch metrics),
`results.png`, `BoxP_curve.png` / `BoxR_curve.png` / `BoxF1_curve.png`,
`confusion_matrix.png`, `confusion_matrix_normalized.png`, `labels.jpg` and
`args.yaml` (the executed configuration `evaluate` reads back).

## `data/experiments/<date>/` — run logs

Small text/JSON records from specific training attempts: `training.log`,
`training.exitcode`, `training_summary.json`, the `dataset.yaml` used, and a
comparison of splits. Useful when reconstructing why a model is what it is.

## Model-card-style images

`docs/images/example-original.jpg` and `example-annotated.jpg` are the README's
input/output pair; `docs/failure_gallery.png` is generated by
`scripts/make_gallery.py`.
